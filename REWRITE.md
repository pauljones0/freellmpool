# Maintained free-access gateway

## Objective and acceptance boundary

Replace the application's fragmented catalog and advisory-only routing core with an authenticated, client-independent proxy that uses legitimate recurring free allowances, keeps provider/model evidence current, and stops or waits when no allowance remains. Finite free allocations cannot promise unlimited throughput or availability. Existing paid balances do not authorize automatic paid use.

This document records the gateway architecture and acceptance boundary. Provider facts come from reviewed official documentation and bounded listing APIs; private account evidence is stored separately. Credentials and prompts must never be committed or sent in public maintenance checks.

## Architecture

1. **Provider registry:** versioned, reviewed provider facts with signup/key links, exact permissions, recurring-free versus trial/paid status, model-list endpoint/parser, free-admission rules, quota scopes/windows/units, source links, and review/expiry dates. Unknown values stay unknown. Account-specific entitlement is separate local state with its own evidence timestamp and expiry; unknown/expired required entitlement denies admission. Catalog refresh cannot renew account entitlement, pricing, or capability evidence. A model appearing in a listing never establishes a free allowance by itself.
2. **Discovery and reconciliation:** provider-specific authoritative GET adapters produce normalized model metadata and complete/partial/error outcomes. Paginated requests remain on the approved origin. A successful complete response can update executable model inventory; a timeout, auth failure, malformed response, or incomplete page sequence cannot erase last-known-good data. Explicit user restrictions and provider tombstones survive refresh. Expired free evidence is ineligible until renewed.
3. **Immutable runtime snapshot:** registry + account entitlement + discovered metadata + local restrictions determine the actual routable models for every modality. Each request captures one generation; new requests observe atomically published updates without restarting the service. Listings expose eligibility, automatic/manual status, verification age, and exclusion reasons.
4. **Allowance ledger:** SQLite transactions reserve all applicable shared limits before network dispatch. Scopes can be account/project, provider, model, IP, or IP+model; key aliases cannot duplicate a shared allowance. Units include requests, input/output/total tokens, weighted neurons, and monetary micro-USD/credits. Windows include rolling intervals, token-bucket refill, calendar day/month in the documented timezone, and anniversary periods anchored to an evidenced signup/first-use date. Unknown reset algorithms or anchors are never substituted with UTC; billable grants remain excluded until their accounting can be established. Concurrency cannot spend the same remaining allowance twice. Reservations use the **final normalized outbound payload**, including reasoning/output floors; adapters cannot inflate a reserved budget afterward. Billable built-in tools/add-ons are rejected unless their costs are explicitly covered. Unknown actual usage retains the conservative reservation; successful usage reconciles it. Failed/aborted requests remain charged conservatively. Runtime provider headers and Retry-After can tighten admission but cannot silently grant paid eligibility or expand a reviewed free limit.
5. **New routing core:** filter by free eligibility, modality, context and current protocol evidence; select available routes across providers; reserve; make one transport attempt; settle usage and scope-aware cooldown; fail over within a bounded request deadline. Never replay after streaming output is committed. When exhausted, return HTTP 429 with a readable reason and Retry-After when a reset/backoff is known (omit it rather than invent an unknown upstream reset), or wait only within an explicit bounded request budget. A manually pinned model still passes the free gate.
6. **Wire compatibility:** retain and test the existing OpenAI Chat Completions, Responses, Anthropic Messages, streaming, embedding and transcription adapters. The rewritten routing core is shared by proxy/CLI/MCP/SDK access. Preserve tested tool-call history behavior. Fix the remaining Host/Origin boundary, MCP negotiation, modality overrides, capability-cache preservation, and evidence-age/probe defects.
7. **Maintenance:** a local daily timer runs authenticated discovery without inference and publishes validated snapshots atomically. A credentialless weekly GitHub workflow checks public model metadata and documented source changes, producing reviewable artifacts/diffs. Neither source text changes nor third-party lists automatically increase allowances or enable paid routes. Document the human review boundary for non-machine-readable pricing and account tiers.
8. **Setup and clients:** `freellmpool setup` is a resumable one-provider-at-a-time wizard focused on recurring free access. Open the official signup page; show exact required fields/permissions; accept hidden input or clipboard; save mode-0600 credentials atomically; perform a listing/auth check; optionally run a bounded free canary through the same ledger; explain actionable failure/skip/resume. Trial/paid choices are skipped by default. A simple bootstrap script installs a pinned checkout/package and launches the wizard. Client presets write reversible configuration for OpenCode, T3 through its actual supported adapter, and Hermes through its current custom-provider mechanism. The local service requires a generated proxy credential and binds loopback by default. **Free client presets contain every inference path inside the gateway:** main, auxiliary, delegated/subagent, and fallback calls. Independent fallback plugins and automatic discovery of other provider keys must be disabled or explicitly limited to the gateway in that profile. This must be verified from effective client configuration, not inferred from the main model setting. Existing unrelated harnesses may remain separately available, clearly outside the free profile.

## Implementation lanes

- Core: allowance ledger, policy/eligibility, immutable runtime and routing, common CLI entry points, migration, integrated validation.
- Catalog: reviewed registry, authoritative adapters, local/history evidence import, last-known-good reconciliation, scheduled maintenance, provider documentation and discovery tests.
- Client/setup: proxy request boundary, MCP negotiation, modality/cache/evidence cleanup as assigned, private resumable onboarding, service/client presets and integration tests.

Before implementation, independent reviews cover product/acceptance, architecture, setup usability, credential/billing security, and operational maintenance. Then three adversarial plan reviews cover feasibility, completeness, and scope/alignment. Tests demonstrating defects precede their fixes. The existing line/branch coverage floors remain mandatory.

## Explicit operational limits

Other applications using the same upstream account may consume quota outside this ledger; provider remaining headers are incorporated where available. Opaque allowances are paced conservatively and learn 429 cooldowns, never displayed as infinite. **Billable-overage accounts require provider-enforced zero-spend or hard free-only request semantics to enter the strict-free pool; otherwise they remain excluded.** A local usage baseline, delayed billing cap, or reservation ledger cannot make a shared billable grant safe against other consumers and never establishes no-charge eligibility. Provider terms, billing and entitlement changes without an API require periodic review even when model IDs update automatically.
